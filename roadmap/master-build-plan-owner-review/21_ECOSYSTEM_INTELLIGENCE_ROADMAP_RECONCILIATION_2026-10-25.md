## Purpose

This reconciliation integrates the ecosystem-intelligence/continuous-learning amendment into the existing Command Center roadmap without discarding verified work, creating duplicate canonical systems, or pretending that documentation alone is implementation.

It applies the amendment's required classification model:

- **EXISTING** — already present and adequate at current branch scope;
- **EXTEND** — existing canonical owner remains authoritative but needs added schema/behavior/tests;
- **NEW** — genuinely new canonical component/work package;
- **LATER** — valid capability sequenced after prerequisites;
- **CONTINUOUS** — permanent operating loop.

## Mandatory pre-C8 intelligence-foundation seam

These work packages become the next required branch-side seam before substantive C8 feature implementation continues.

### IF-1 — Shared intelligence contracts and ontology

Implement/extend canonical IDs, ontology types, epistemic states, temporal claim fields, causal-claim separation, provenance, applicability scope and version compatibility.

**Gate:** schema/contract tests reject ambiguous truth, incompatible ontology/version, missing provenance and unauthorized scope.

### IF-2 — Capability / Method Portfolio

Extend the canonical capability registry to support multiple methods, conditions, alternatives, performance history, fallback, risk, lifecycle and verification.

**Gate:** two valid competing methods can coexist and routing can select conditionally without changing core code.

### IF-3 — Specialist Model Registry

Extend specialist registration with authority relationship, scope, data class, capabilities/methods, permissions, calibration/evaluation, dependency, failure/fallback, learning eligibility and retirement state.

**Gate:** a subordinate specialist cannot self-expand scope or become a peer control plane.

### IF-4 — Learning Packet + Promotion Governance

Add canonical Learning Packet schema and promotion lifecycle.

**Gate:** unvalidated/private/unsupported learning cannot become global operational policy; scoped alternatives remain separately versioned.

### IF-5 — Epistemic / Contradiction / Uncertainty Layer

Extend knowledge/provenance for explicit epistemic states, contradiction records, uncertainty propagation, stale-state handling and calibration evidence.

**Gate:** conflicting and weak evidence remains visibly conflicting/uncertain rather than being flattened into certainty.

### IF-6 — Layered Memory + Revalidation + Context Compiler

Extend governed memory and Context Builder with layered scopes, decay/revalidation, negative/procedural memory and applicability-aware context compilation.

**Gate:** relevant context is minimal, fresh, policy-compliant and cannot leak unrelated company/project data.

### IF-7 — Evaluator / Outcome / Decision-Quality Foundation

Add evaluator registry, benchmark-class semantics and outcome records that preserve information available at decision time, predictions, confounders and actual results.

**Gate:** benchmark/shadow/canary/production evidence cannot be conflated and outcome luck cannot automatically rewrite method quality.

### IF-8 — Negative Knowledge + Transferability

Add negative-knowledge and transferability records.

**Gate:** known failed/unsafe methods remain discoverable with scope; cross-system reuse requires compatibility/evidence rather than similarity alone.

### IF-9 — Trace + Dependency + Version Integration

Extend trace and dependency/version graph across method selection, specialists, evaluators, learning packets, promotions and procedures.

**Gate:** a decision and subsequent learning can be traced to exact versions/evidence and stale dependents can be detected.

### IF-10 — Self-Improvement / Recovery Invariants

Encode improvement lifecycle and intelligence-state recovery constraints.

**Gate:** no learned change silently mutates production; recovery cannot resurrect revoked access, invalidated learning or superseded policy.
